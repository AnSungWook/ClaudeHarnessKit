# ADR-018: 바깥 HTTP 는 클라이언트 하나로 부르고, 타임아웃은 클라이언트마다 적으며, 재시도는 멱등 호출에만 건다

## Status

Accepted

## Date

2026-11-02

## Intent

바깥 시스템이 느리거나 죽어도 우리 쪽 스레드가 묶이지 않고, 두 번 가면 안 되는 요청이 두 번 가지 않게 한다.

## Context

- 기존 상태: 같은 저장소 안에서 HTTP 클라이언트가 여러 종류(`RestTemplate`, `WebClient`, OkHttp, 직접 `HttpClient`)로 섞여 있다. 타임아웃은 라이브러리 기본값에 맡긴다. 실패하면 무엇이든 다시 보낸다. 바깥 응답 JSON 을 도메인 객체로 바로 받는다.
- 문제점: 클라이언트가 둘이면 타임아웃, 재시도, 예외 감싸기가 두 갈래로 갈린다. 기본 타임아웃이 무한이거나 길면 바깥 하나가 멈출 때 우리 스레드 풀이 다 묶인다. 결제, 발송 같은 쓰기를 재시도하면 두 번 처리된다. 바깥 칸 이름이 바뀌면 도메인까지 흔들린다.
- 제약 조건: 클라이언트 종류는 스택이 정한다(서블릿이면 동기, 리액티브면 리액티브). 이 ADR 은 종류가 아니라 "하나로, 보이게" 를 정한다.

## Decision

**한 저장소의 바깥 HTTP 는 클라이언트 한 종류로, 어댑터 안에서만 부르고, 타임아웃과 재시도는 클라이언트마다 눈에 보이게 적는다.**

- 클라이언트 종류는 저장소마다 하나다. Spring MVC(서블릿)면 `RestClient` 다. 같은 일을 하는 다른 클라이언트를 새로 들이지 않는다.
- 클라이언트는 바깥 어댑터(ADR-005 의 `adapter/out`) 안에서만 쓴다. 서비스는 클라이언트 타입을 모른다. 클라이언트 빈은 설정이 이름 붙여 내고 어댑터가 주입받는다(ADR-008).
- 연결 타임아웃과 읽기 타임아웃은 클라이언트마다 설정 객체에 적는다(ADR-003). 라이브러리 기본값에 기대지 않는다. 길어야 하는 호출은 그 클라이언트 설정에서 늘리고 이유를 적는다.
- 재시도는 멱등 호출에만 건다. 조회와, 같은 키로 다시 보내도 결과가 같은 쓰기다. 두 번 가면 안 되는 호출은 재시도하지 않는다. 재시도 여부는 실패 종류(타임아웃, 5xx, 429 는 다시, 4xx 는 안 함)로 가른다.
- 바깥 요청과 응답은 그 클라이언트 전용 타입(record)으로 둔다. 도메인 값을 바깥 본문으로 그대로 직렬화하지 않는다. 바깥 칸 이름을 맞추는 `@JsonProperty` 는 그 타입에만 단다. 바깥 응답을 도메인 값으로 바꾸는 일은 어댑터가 한다.
- 바깥 예외(`RestClientException` 등)는 어댑터에서 사유 예외로 감싼다(ADR-006). `cause` 를 달고, 서비스까지 라이브러리 예외가 올라오지 않는다. 응답 크기에도 상한을 둔다.
- 클라이언트 테스트는 4xx, 5xx, 429, 연결 실패, 읽기 타임아웃이 각각 어느 실패로 가는지 보인다(ADR-012).

### 체크리스트

- [ ] 저장소 안 HTTP 클라이언트가 한 종류다(`RestTemplate`, `WebClient`, OkHttp 가 새로 들지 않았다)
- [ ] 클라이언트를 바깥 어댑터와 설정 밖에서 쓰지 않는다
- [ ] 클라이언트마다 연결, 읽기 타임아웃이 설정에 적혀 있다
- [ ] 멱등이 아닌 쓰기 호출에 재시도가 없다
- [ ] 바깥 요청, 응답이 전용 타입이고 도메인 타입을 바로 직렬화하지 않는다
- [ ] 라이브러리 예외가 어댑터 밖으로 나가지 않는다
- [ ] 클라이언트 테스트가 실패 갈래(4xx, 5xx, 429, 연결 실패, 타임아웃)를 보인다

### 안티패턴

| 안티패턴 | 올바른 패턴 |
|---------|-----------|
| 서비스가 `restClient.get()...` 을 직접 부른다 | 포트 뒤 어댑터가 부르고 서비스는 포트만 안다 |
| 타임아웃 설정 없이 `RestClient.create()` | 설정 객체의 `connectTimeout`, `readTimeout` 으로 만든 클라이언트 빈 |
| 결제 승인 요청에 `@Retryable` | 조회와 멱등 키 있는 쓰기에만 재시도 |
| 바깥 응답을 `Order` 엔티티로 바로 받는다 | `PgApproveResponse` record 로 받고 어댑터가 도메인 값으로 바꾼다 |
| `catch (RestClientException e) { throw e; }` 를 서비스에서 | 어댑터에서 `PaymentGatewayUnavailableException(cause)` 로 감싼다 |

## 다른 언어에서

- 원칙(클라이언트 하나, 어댑터 안에서만, 타임아웃 명시, 멱등에만 재시도, 바깥 전용 타입, 예외 감싸기)은 같다. `RestClient` 는 Spring 의 예다.
- Kotlin: Spring 이면 같다. Ktor 클라이언트를 쓰면 `HttpTimeout` 플러그인으로 클라이언트마다 적는다.
- TypeScript(Node): `fetch` 나 axios 중 하나로. `AbortSignal.timeout()` 이나 axios `timeout` 을 클라이언트 인스턴스마다. 응답은 스키마(zod)로 검증한 전용 타입으로 받는다.
- Python: httpx 나 requests 중 하나로. `timeout=` 을 늘 넘기고(requests 는 기본이 무한), 재시도는 tenacity 를 멱등 호출에만. 응답은 pydantic 모델로.

## Consequences

### 긍정적
- 바깥 하나가 멈춰도 타임아웃에서 끊겨 우리 스레드가 묶이지 않는다.
- 두 번 처리되는 사고가 줄어든다.
- 바깥 칸 이름이 바뀌어도 어댑터 하나만 고친다.

### 부정적
- 바깥 전용 타입과 변환 코드가 늘어난다.
- 클라이언트마다 타임아웃 값을 정하고 운영에서 조정해야 한다.
