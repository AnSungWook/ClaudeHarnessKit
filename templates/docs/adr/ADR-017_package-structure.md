# ADR-017: 패키지는 기능별로 나누고, 그 안은 성격별 폴더로 고정한다

## Status

Accepted

## Date

2026-10-30

## Intent

폴더 이름만 보고 그 안에 무엇이 있는지 알게 하고, 어느 저장소를 열어도 같은 자리에 같은 성격의 코드가 있게 한다. ADR-005 의 층(역할)이 폴더에 그대로 드러나게 한다.

## Context

- 기존 상태: 한 패키지 안에 엔티티, 설정, 서비스, 컨트롤러가 섞여 있다. 같은 회사의 두 저장소가 서로 다른 모양이다(한쪽은 성격별, 한쪽은 기능별에 제각각인 하위 폴더). `api` 라는 폴더에 컨트롤러는 없고 모듈 사이에 공개하는 값(정책, 이력, 종류)이 들어 있는 식으로, 흔한 뜻과 다른 이름을 쓴다.
- 문제점: 처음 보는 사람이 "컨트롤러는 어디, 설정은 어디" 를 저장소마다 새로 찾는다. 이름이 흔한 뜻과 달라 잘못 읽는다. 역할은 문서(대응표)에만 있고 폴더에 없어서, 리팩토링할 때도 폴더 정리는 범위에서 빠진다.
- 제약 조건: 이미 커진 저장소를 한 번에 옮기면 diff 와 진행 중인 브랜치 충돌이 크다.

## Decision

**새 저장소의 기본 배치는 최상위를 기능(업무 단위)으로 나누고, 각 기능 안은 아래 성격별 폴더로 고정한다. 이름과 자리를 바꾸지 않는다. 기존 저장소는 아래 「판정 기준」대로 그 저장소가 고른 배치를 따른다.**

```
<루트 패키지>/
├── <기능>/                        # 주문, 결제, 정산처럼 업무 단위 하나
│   ├── domain/                    # 값, 도메인 모델, 판단, 도메인 서비스 (ADR-002)
│   │   └── exception/             # 그 기능의 사유 예외 (ADR-006)
│   ├── application/
│   │   ├── port/
│   │   │   ├── in/                # 유스케이스 interface - 다른 기능과 바깥이 부르는 입구
│   │   │   └── out/               # 바깥에 기대는 약속 interface (저장, 외부 호출)
│   │   └── service/               # 유스케이스 구현 - 흐름만, 트랜잭션 경계 (ADR-014)
│   ├── adapter/
│   │   ├── in/
│   │   │   ├── web/               # 컨트롤러, 요청·응답 DTO (ADR-005, ADR-013)
│   │   │   ├── event/             # 이벤트 수신 리스너 - 유스케이스에 넘기기만 (ADR-001)
│   │   │   ├── schedule/          # 스케줄 실행을 받는 트리거 메서드
│   │   │   └── batch/, message/   # 배치 잡 실행 입구, 메시지 수신 등 다른 입구
│   │   └── out/
│   │       ├── persistence/       # 영속 엔티티, 리포지토리·SQL 매퍼, out 포트 구현
│   │       └── client/            # 외부 API 호출, out 포트 구현
│   └── config/                    # 그 기능의 빈 조립, 설정 객체 (ADR-003), 잡 정의·스케줄러 실행기 조립
└── shared/                        # 여러 기능이 같이 쓰는 것만. 최소로 유지
```

- **폴더 이름은 고른 배치의 이름만 쓴다(기본 배치면 위 목록).** `api`, `common`, `util`, `helper`, `manager`, `etc`, `impl`, `core` 를 기능 안 폴더 이름으로 쓰지 않는다(ADR-016). 특히 `api` 는 HTTP API 로 읽히므로, 모듈이 공개하는 입구는 `application/port/in`, 공개하는 값은 `domain` 에 둔다.
- **한 폴더에는 한 성격만.** 기본 배치라면 컨트롤러는 `adapter/in/web` 에만, 설정은 `config` 에만, 영속 엔티티는 `adapter/out/persistence` 에만 둔다. 섞이면 위반이다.
- **바깥에서 실행을 시작시키는 입구는 고른 배치에서 인바운드 어댑터 역할을 하는 폴더에만 둔다(기본 배치면 `adapter/in/*`).** HTTP 요청, 스케줄 실행, 메시지 수신, 이벤트 수신, 명령행 Runner 가 입구다. "이 앱이 언제 무엇을 시작하나" 를 그 폴더만 보고 알게 한다(ADR-001 「서비스에 안 보이는 흐름」).
  - 잡이나 스케줄러를 **조립하는** 설정(잡 정의 빈, 스케줄러 실행기, 리스너 컨테이너 설정)은 `config` 에, 실행을 **받는** 쪽(`@Scheduled` 트리거 메서드, 잡 실행 입구, 리스너 메서드)은 인바운드 어댑터에 둔다.
  - 입구는 받은 것을 유스케이스에 넘기기만 한다. 다른 기능의 이벤트를 받는 리스너도 그 이벤트 타입은 발행한 기능의 `domain` 에서 import 한다.
- **아래 경로(`application/port/in`, `adapter/out/persistence` 등)는 기본 배치 기준이다.** 다른 배치를 고른 저장소는 같은 역할의 폴더에 같은 규칙을 적용한다(예: 성격별 최상위면 `repository/` 가 `adapter/out/persistence` 역할).
- **`persistence/` 의 매퍼는 SQL 매퍼(MyBatis Mapper 인터페이스)만 뜻한다.** 객체를 다른 객체로 바꾸는 Mapper 클래스는 아니고, 그런 변환은 만들어지는 타입의 `of(원본)` 이다(ADR-002).
- **기능 사이 호출은 상대 기능의 `application/port/in` 과 `domain` 의 공개 값으로만.** 상대의 `adapter`, 영속 엔티티, `service` 구현을 import 하지 않는다. 영속 엔티티도 예외가 없다.
- **다른 기능의 영속 엔티티는 키 칸으로만 가리킨다.** 엔티티는 상대를 키 칸(`Long categoryId` 처럼)으로 든다. 객체 참조(`@ManyToOne` 등 연관)도, 상대 표와 잇는 쿼리(조인, 두 표 `from`, 상대 표 서브쿼리)도 두지 않는다 - 두 표가 같은 DB 에 있어도 같다.
  - 상대 값이 필요하면 상대 `port/in` 에 키 목록을 받는 메서드를 두고, 유스케이스 서비스가 키를 모아 한 번 부른다 - 행마다 부르지 않는다.
  - 상대 칸으로 거르는 조회는 서비스가 상대 `port/in` 에서 키를 먼저 받고, 그 키 목록으로 내 저장소를 읽는다. 상대 칸으로 정렬하는 페이지 조회처럼 한 쿼리로만 되는 것은 그 칸을 내 표에도 두거나, 그 조회 하나만 예외로 그 저장소 ADR 에 사유와 함께 적는다.
  - 내 엔티티의 메서드가 상대 값으로 판단해야 하면 서비스가 그 값을 인자로 넘긴다(`order.isRefundable(category.refundPolicy())` 처럼).
  - 읽어 온 두 기능의 값을 짝 지어 판단까지 하면, 그 짝 맞추기와 판단은 서비스가 아니라 묶음 타입(일급 컬렉션)이 든다(ADR-002).
  - 그래서 다른 기능의 영속 엔티티는 어디서도 import 하지 않는다.
  - 같은 기능 안의 표끼리 연관과 조인을 얼마나 허용할지는 저장소 ADR 이 정한다(DB 와 영속 기술에 달린 규격이다).
- **의존 방향은 ADR-005 그대로**: `adapter` → `application` → `domain`. `domain` 은 다른 폴더를 import 하지 않는다.
- **작은 기능은 폴더를 줄여도 된다.** 바깥 입구가 하나뿐이면 같은 기능의 인바운드 어댑터(`adapter/in`)는 `port/in` 없이 `application/service` 를 바로 부를 수 있다(다른 기능은 이때도 `port/in` 으로만 부른다). 그리고 외부 호출이 없으면 `adapter/out/client` 를 만들지 않는다. 다만 있는 폴더의 이름과 자리는 바꾸지 않는다.
- **리팩토링의 범위에는 패키지 정렬이 기본으로 들어간다.** 구조·설계 리팩토링을 하면 그 범위의 파일이 저장소가 고른 배치와 다른지 보고 같이 옮긴다. 따로 지시하지 않아도 한다. 옮기는 커밋은 기능 변경 커밋과 나눈다(ADR-007).
- **판정 기준은 저장소가 고른 배치다. 기본은 위 배치이고, 기존 저장소는 그 저장소 ADR 이나 README 에 고른 배치다. 이미 구조가 있는 저장소에서 모양이 섞여 있으면, 그 저장소의 현재 구조에 더 어울리는 한 가지 모양을 골라 저장소 전체를 그 모양으로 일관되게 맞춘다.**
  - 고르는 기준: 그 저장소에서 이미 가장 많이 쓰는 모양, 옮길 파일이 가장 적은 모양, 의존 방향(ADR-005)이 폴더에 가장 잘 드러나는 모양 순서로 본다. 예를 들어 저장소 전체가 성격별 최상위(`controller/`, `service/`, `repository/`)로 굳어 있으면 그 모양으로 맞추고, 기능별 최상위가 대부분이면 기능 안 성격 폴더를 위 이름으로 맞춘다.
  - 고른 모양과 그 이유는 그 저장소의 ADR(기본 ADR 다음 번호부터)이나 `README.md` 에 적는다. 그 뒤로는 새 코드도 그 모양을 따른다.
  - 어느 모양을 고르든 지키는 것: 한 폴더에 한 성격, 뭉뚱그린 폴더 이름(`api`, `common`, `util` 등) 금지, 의존 방향(ADR-005).
  - 옮기는 것은 기능(또는 폴더) 하나씩, 이동 커밋을 따로 낸다. 옮기는 동안 두 구조가 공존하는 것은 옛 폴더 ↔ 고른 배치 대응표가 문서에 있을 때만 허용하고, 다 옮기면 대응표를 걷는다.

### 체크리스트

- [ ] 새 파일이 저장소가 고른 배치(기본은 위 배치)의 자리에 있다
- [ ] 뭉뚱그린 폴더 이름(`api`, `common`, `util` 등)이 없다
- [ ] 한 폴더에 컨트롤러·설정·엔티티·서비스가 섞여 있지 않다
- [ ] 입구(컨트롤러, `@Scheduled` 트리거, 메시지·이벤트 리스너, Runner)가 인바운드 어댑터 역할 폴더에만 있고, 잡·스케줄러 조립은 `config` 에 있다
- [ ] 다른 기능의 `adapter`, 영속 엔티티, `service` 구현을 어디서도 import 하지 않는다
- [ ] 다른 기능 엔티티는 키 칸으로만 들고, 연관도 상대 표와 잇는 쿼리도 없다
- [ ] 다른 기능 값은 서비스가 상대 `port/in` 에서 키 목록으로 한 번에 받는다(행마다 부르지 않는다)
- [ ] 구조 리팩토링 PR 에 패키지 정렬이 들어 있다(또는 안 한 이유가 적혀 있다)
- [ ] 기존 저장소라면 고른 한 가지 모양이 그 저장소 ADR 이나 README 에 적혀 있고, 두 모양이 공존하면 대응표가 있다
- [ ] `persistence/` 의 매퍼가 SQL 매퍼뿐이고 객체 변환 Mapper 클래스가 없다
- [ ] `port/in` 없이 서비스를 바로 부르는 쪽이 같은 기능의 인바운드 어댑터뿐이다
- [ ] 파일 이동 커밋과 기능 변경 커밋이 나뉘어 있다

### 안티패턴

| 안티패턴 | 올바른 패턴 |
|---------|-----------|
| `order/api/` 에 정책·이력 record, 컨트롤러는 `order/web/` | 공개 값은 `order/domain/`, 입구는 `order/application/port/in/`, 컨트롤러는 `order/adapter/in/web/` |
| `order/` 한 폴더에 `OrderController`, `OrderConfig`, `OrderEntity`, `OrderService` | 성격별 폴더로 나눈다 |
| 새 저장소를 `controller/`, `service/`, `repository/` 로만 가르기(기능이 흩어짐) | 기능이 최상위, 성격은 그 안 |
| 고른 배치를 적지 않고 옛 구조와 새 구조를 섞어 둠 | 고른 배치를 저장소 ADR 이나 README 에 적고, 옮기는 동안은 대응표를 둔다 |
| `payment` 가 `order/adapter/out/persistence/OrderEntity` 를 import | `order/application/port/in` 의 유스케이스를 부른다 |
| 다른 기능 엔티티에 `@ManyToOne` 을 걸고 서비스에서 `order.getCategory().getName()` | 키 칸 + 서비스가 `port/in` 에 키 목록으로 한 번 조회 |
| 내 영속 어댑터가 `join ... on o.categoryId = c.id` 로 다른 기능 표를 잇는다 | 서비스가 상대 `port/in` 에서 키를 먼저 받고 그 키 목록으로 내 표를 읽는다 |
| 엔티티 메서드가 판단하려고 다른 기능 엔티티에 연관을 건다 | 서비스가 판단에 쓸 값을 인자로 넘긴다 |
| `order/application/service/OrderService` 안에 `@Scheduled` 메서드와 `@EventListener` 메서드 | 트리거는 `adapter/in/schedule`, 리스너는 `adapter/in/event` 에 두고, 각각 같은 기능의 `port/in` 을 통해 유스케이스에 넘긴다 |
| 리팩토링 PR 에서 클래스만 고치고 폴더는 그대로 | 범위의 파일을 저장소가 고른 배치로 같이 옮긴다 |
| `common/`, `util/` 에 아무 기능의 코드나 모음 | 주인 기능으로 옮기고, 진짜 공용만 `shared/` |

## 다른 언어에서

- Kotlin: 같은 배치를 그대로 쓴다.
- TypeScript(NestJS): `src/<기능>/` 아래 `domain/`, `application/`, `adapter/in/http/`(컨트롤러), `adapter/out/persistence/`, 모듈 파일(`<기능>.module.ts`)은 `config` 자리에 둔다.
- Python: `<패키지>/<기능>/` 아래 같은 하위 패키지(`domain`, `application`, `adapter/inbound/web`, `adapter/outbound/persistence`). `in` 은 예약어라 `inbound`/`outbound` 로 쓴다.

## Consequences

### 긍정적
- 어느 저장소든 같은 자리에서 같은 성격의 코드를 찾는다.
- 층(ADR-005)이 폴더에 드러나, import 경로만 보고 의존 방향 위반을 알아챈다(아키텍처 테스트로 검사하기도 쉽다).
- 리팩토링 때 구조가 같이 정리돼 "역할은 문서에만 있는" 상태가 다시 생기지 않는다.
- 기능 사이에 숨은 쿼리(지연 로딩)가 없어 어떤 표를 읽는지 서비스에 다 보이고, 기능을 다른 저장소나 서비스로 떼어 낼 때 고칠 자리가 `port/in` 호출로 좁혀진다.

### 부정적
- 폴더 깊이가 깊어진다.
- 조인 한 번이던 조회가 기능마다 한 번씩으로 늘고, 상대 칸으로 정렬하는 페이지 조회가 불편해진다.
- 기존 저장소를 옮기는 동안은 두 모양이 섞인다(대응표를 두는 동안만).
