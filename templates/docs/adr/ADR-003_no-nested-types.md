# ADR-003: 중첩 타입은 업무가 실제로 겹칠 때만 쓴다

## Status

Accepted

## Date

2026-10-30

## Intent

값의 주인이 타입 이름에 드러나게 하고, 그 값의 팩토리와 판단(ADR-001)을 둘 자리가 바깥 파일 안으로 숨지 않게 한다.

## Context

- 기존 상태: `Order.Line`, `Run.Attempt` 처럼 클래스 안에 record·class·enum·interface 를 넣어 쓴다.
- 문제점: 바깥 클래스 이름을 달고 다니는 타입은 독립된 값인데도 바깥의 부속처럼 보이고, 그 값의 판단 메서드가 바깥 파일에 섞인다. 검색과 재사용도 어렵다.
- 제약 조건: sealed 결과 타입처럼 바깥과 갈래가 함께 읽혀야 뜻이 서는 경우는 떼면 오히려 찾아다녀야 한다.

## Decision

**일반적으로 중첩 타입을 쓰지 않고 같은 패키지의 최상위 타입으로, 뜻이 드러나는 이름으로 둔다(`Run.Attempt` → `RunAttempt`).**

- 중첩을 허용하는 경우는 하나 - 바깥 타입과 업무가 실제로 겹쳐 중첩이 이해를 도울 때. 셋을 다 만족해야 한다.
  1. 바깥 타입 없이는 뜻이 없다.
  2. 같이 읽어야 이해된다.
  3. 바깥 업무 밖에서 따로 쓰이지 않는다.
  - 예: sealed `Outcome` 과 그 갈래 `Outcome.Success`, `Outcome.Failure`.
- 남긴 중첩 타입은 이유를 남긴다 - 아키텍처 테스트의 허용 목록에 "바깥.안 - 왜 같이 읽어야 하는가".
- 꺼내 옮겨도 직렬화(JSON·YAML) 모양은 바꾸지 않는다.

### 체크리스트

- [ ] 새 중첩 타입이 위 세 조건을 다 만족한다
- [ ] 허용 목록에 이유 없는 중첩 타입이 없다
- [ ] 꺼낸 타입의 이름이 바깥 이름 없이도 뜻이 드러난다
- [ ] 옮긴 뒤 직렬화 모양이 그대로다

### 안티패턴

| 안티패턴 | 올바른 패턴 |
|---------|-----------|
| `class OrderService { record Line(...) {} }` | 같은 패키지의 `OrderLine` |
| `private` 이니 괜찮다며 중첩 | 가시성이 아니라 업무 관계로 판단 |
| 중첩 record 안에 판단 메서드를 넣어 바깥 파일이 비대해짐 | 최상위 타입으로 꺼내 팩토리·판단을 그 파일에 |
| 결과 갈래(sealed)까지 전부 떼어 파일을 흩뿌림 | 바깥과 같이 읽혀야 하는 갈래는 중첩 허용 + 이유 기록 |

## Consequences

### 긍정적
- 타입 이름만으로 값의 주인이 보인다.
- 값마다 자기 파일에 팩토리·판단을 둘 수 있다.

### 부정적
- 파일 수가 는다.
- "업무가 겹친다" 의 판단이 리뷰에 기대므로, 허용 목록과 이유 기록이 필요하다.
