# ADR-001: 입력을 받은 자리부터 사람이 따라 읽을 수 있게 짠다

## Status

Accepted

## Date

2026-11-03

## Intent

입력(요청, 실행 명령, 메시지)을 받은 자리에서 읽기 시작한 사람이, 이름만 보고 각 단계가 무슨 일을 하는지 알며 끝까지 따라갈 수 있게 한다.

이 ADR 이 나머지의 전제다. 코드를 누가 짜든(사람이든 AI 든) 결국 사람이 읽고 확인한다. 따라 읽을 수 없으면 다른 ADR 을 지켰는지도 확인할 수 없다.

## Context

- 기존 상태: 기능을 붙일 때마다 클래스, 래퍼, 콜백이 늘고, 그 이름이 맡은 일 대신 구현 수단(잡아 둠, 감쌈, 흘려보냄)을 말한다.
- 문제점: 입구를 열면 `stream(runs.x(key), response)`, `claim()`, `holding()` 처럼 읽어도 뜻을 모르는 호출이 이어진다. 안을 다 열어야 흐름이 보이고, 실제 처리는 그 안쪽에 묻힌다.
- 제약 조건: 클래스 수, 층 수, 위임 자체는 문제가 아니다. 층 나눔(ADR-005)과 판단의 소유(ADR-002)는 그대로 지킨다.

## Decision

**입력을 받은 자리에서 이름만 읽어 내려가도 "이 흐름에서는 이 일을 하는구나" 를 알 수 있게 짠다.**

- **누가 판정하나.** 그 코드를 맡긴 사람(코드의 주인)이 읽히는지가 기준이다. 그 사람이 코드를 보고 업무를 이해해야 하기 때문이다. 주인이 따라가지 못한 자리는 고친다. 흐름 글을 적는 PR 에서는 그것을 판정 근거로 삼는다(적용 대상과 적는 법은 ADR-020).
- **이름은 호출식 전체로 본다.** 받는 객체, 메서드, 인자를 업무 용어와 함께 읽는다. `OrderResponse.of(order)`, `orders.findById(orderId)` 처럼 규칙 이름(`of`, `get`, `find`)이 들어간 호출식도 전체가 뜻을 말하면 괜찮다.
- **흐름의 단계는 맡은 일을 말한다.** 구현 수단만 말하는 이름(`run`, `handle`, `process`, `execute`, `claim`, `holding`, `stream`)으로 단계를 나타내지 않는다. 프레임워크 계약 메서드(`Runnable.run`, `Tasklet.execute`)는 예외이고, 그것을 부르는 우리 쪽 호출식이 맡은 일을 말하면 된다.
- **익숙한 구조를 드러낸다.** Controller → Service, Job → Step, Listener → Handler 처럼 프레임워크를 아는 사람이 기대하는 구조가 코드에서 그대로 보이게 둔다. 프레임워크가 주는 것을 같은 일의 자체 타입으로 다시 감싸지 않는다.
- **콜백, 넘기는 작업, 파이프라인은 쓴다.** 등록·넘기는 자리에서 무슨 일이 언제 도는지 보이면 된다. 이벤트와 AOP 는 아래 「서비스에 안 보이는 흐름」 절이 더 좁힌다.
  - 언제 도는지는 호출식, 리스너 선언, 등록 설정에서 보이면 된다(`@TransactionalEventListener(phase = AFTER_COMMIT)`, `@Async("mailExecutor")`).
  - 파이프라인은 전체에 업무 목적 이름을 주고(`buildUnpaidReminderMails(orders)`), 뜻이 안 보이는 연산만 뽑아 이름을 붙인다.
- **이름으로 내용을 알 수 없는 실행 객체를 돌려주지 않는다.** 람다를 든 홀더, "잡아 둔 실행" 을 돌려줘 호출한 쪽이 그 안을 뒤져야 무엇이 실행되는지 아는 구조다.

### 서비스에 안 보이는 흐름: 이벤트, AOP, 자동 실행

입구와 서비스를 읽는 사람에게 보이지 않는 자리에서 일이 돌면, 이름을 잘 지어도 흐름을 따라갈 수 없다. 그래서 위의 "콜백, 넘기는 작업도 쓴다" 를 이벤트와 AOP 에서는 아래처럼 좁힌다. 무엇을 막는지의 원칙은 여기 두고, 폴더 위치·선언 모양·허용 목록 같은 기계 검사는 킷의 관례로 `checks/` 에 둔다.

**이벤트**

- **응답하기 전에 끝나야 하는 일은 명시적으로 부른다.** 명시적 호출은 서비스(ADR-005 의 서비스 층)가 포트, 도메인, 다른 기능의 입구(`port/in`)를 부르는 것이다. 어댑터끼리 부르거나 서비스가 어댑터를 직접 부르는 것이 아니다.
- **나중에라도 반드시 끝나야 하는 일은 그 책임을 지금 트랜잭션에 남긴다.** 업무 저장과 같은 트랜잭션에서 처리할 일을 영속화하고(아웃박스 등), 전달·재시도·중복 처리를 그 저장소 ADR 에서 정한다. 외부 호출과 DB 저장은 원자적이지 않다(ADR-014).
- **이벤트는 실패해도 지금 요청의 결과를 바꾸지 않는 후속 일에 쓴다.** 다른 기능에 넘길 때, 또는 같은 기능의 커밋 뒤 실행(ADR-014)이다. 늦게 돌리고 싶다는 이유만으로 들이지 않는다.
- **이벤트를 골랐으면 실행 시점과 실패 처리를 같이 정한다.** 동기 리스너의 예외는 발행한 호출로 번져 요청을 실패시킨다. 커밋 뒤 리스너는 커밋 뒤 장애 때 일을 잃을 수 있고, 활성 트랜잭션 없이 발행하면 돌지 않는다(`fallbackExecution` 은 리뷰 대상). 실패를 격리했으면 기록·재시도·운영 확인을 누가 하는지도 정한다. 예외를 삼키거나 `@Async` 만 붙여 해결하지 않는다.
- **업무 순서는 서비스의 호출 순서로 드러낸다.** 리스너의 `@Order` 에 꼭 지켜야 할 순서를 숨기지 않는다. 리스너가 반환값으로 다음 이벤트를 발행하지 않는다.
- **이벤트 타입은 일어난 사실을, 받는 쪽은 하는 일을 말한다**(`OrderPlacedEvent` → `sendReceiptOnOrderPlaced`). 이벤트 타입은 발행한 기능이 공개하는 값이라 그 기능의 `domain` 에 둔다(ADR-017). 도메인에 Spring 의존을 넣지 않는다.
- **리스너는 받은 사실을 유스케이스에 넘기기만 한다.** 받는 기능의 `port/in` 에 넘긴다. 같은 기능의 `application/service` 를 바로 부르는 것은 ADR-017 의 생략 조건(바깥 입구가 하나뿐인 작은 기능)을 만족할 때만이다 - 리스너도 입구 하나로 센다. out 어댑터는 직접 부르지 않는다. 커밋 뒤 바깥 호출은 트랜잭션 밖에서 하고 결과 저장만 짧은 트랜잭션으로 한다. 리스너 메서드에 `@Transactional` 을 붙여 ADR-014 를 돌아가지 않는다. 비동기 리스너는 정해진 실행기를 쓴다(ADR-015).
- **이벤트에는 필요한 키와 값만 싣는다.** 영속 엔티티나 요청 객체를 싣지 않는다. 인증 토큰·자격 증명은 싣지 않는다. 개인정보는 필요한 최소한만 싣고, 그 이벤트를 저장하는 자리(아웃박스, 메시지 큐)의 보관 기간·접근 범위와 로그 노출을 통제한다(ADR-011, ADR-013). 비동기·커밋 뒤 실행은 요청 스레드의 인증·테넌트 문맥을 가정하지 않고 필요한 값을 명시적으로 넘긴다. 넘겨받은 사용자·테넌트 키는 권한의 증명이 아니라서, 받는 유스케이스가 권한과 범위를 다시 확인한다.

**AOP**

- **동작을 바꾸는 advice 는 적용되는 메서드나 클래스에 표시가 보여야 한다.** 권한, 트랜잭션, 재시도, 캐시, 인자·반환값 바꾸기가 그렇다. 표시 이름과 선언에서 무엇을 어디까지 하는지 읽혀야 한다. `@BusinessAction` 처럼 뜻이 모호한 자체 표시는 만들지 않는다.
- **표시가 있어도 각 ADR 이 그대로 걸린다.** `@Transactional` 은 서비스 메서드에만(ADR-014), 재시도는 어떤 일이든 대상 예외, 횟수, 시간 상한을 적고 다시 해도 결과가 같은(멱등) 일에만 건다. 바깥 HTTP 호출의 재시도 기준은 ADR-018 이 더 자세히 정한다. 재시도와 트랜잭션의 적용 순서처럼 업무에 중요한 조합은 테스트로 확인한다. 같은 클래스 안의 호출은 프록시를 안 거쳐 advice 가 돌지 않는다.
- **표시 없이 패턴으로 거는 advice 는 관측(로그, 메트릭, 추적)만 한다.** 인자·반환값·업무 상태를 바꾸지 않고, 예외를 삼키거나 바꾸지 않고, 업무 실행을 재시도하지 않는다. 관측 코드도 예외를 던지거나 개인정보를 남기면 위반이다(ADR-011).
- **중앙 보안 설정은 예외다.** HTTP 필터 체인의 접근 제어처럼 설정 한 자리에서 위치와 적용 범위가 추적되면, 메서드에 표시가 없다는 이유로 막지 않는다(ADR-019).

**리뷰에서 같이 보는 숨은 흐름**

아래 범주는 "그 흐름이 어디 선언돼 있는지 한 자리에서 찾을 수 있나" 로 본다. 항목은 예시다.

- 요청 전후: 서블릿 필터, MVC 인터셉터, 요청·응답 advice, 보안 필터 체인
- 자동 실행: `@PostConstruct`, `ApplicationRunner`·`CommandLineRunner`, 종료 훅
- 조립에 따른 경로 바뀜: `@Profile`, `@Conditional*`, `@Primary`, `@Qualifier`, 빈 목록과 그 순서
- 늦게·갈라져 도는 일: `@Async`, Future 콜백, 캐시, 재시도·서킷브레이커, 트랜잭션 동기화 콜백
- 메시지 실패 경로: ack 시점, 재전달, 재시도 소진, DLQ, 중복 수신

바깥에서 실행을 시작시키는 입구를 두는 자리는 ADR-017 이 정한다. 같은 기능 안의 연관·조인(ADR-017 이 저장소 ADR 에 맡김), JPA 영속성 콜백, DB 트리거는 이 절이 다루지 않는다.
- **ADR-016 과 나눔.** 낱말 하나가 뜻을 드러내는지는 ADR-016, 단계를 이어 읽을 때 흐름이 보이는지는 이 ADR 이 본다. 한 자리는 하나로만 지적한다.

### 체크리스트

- [ ] 코드의 주인이 코드 이름만으로(흐름 글을 적는 PR 이면 그 글과 함께) 흐름을 따라간다
- [ ] 흐름의 단계를 나타내는 호출식이 맡은 일을 말한다(프레임워크 계약 메서드는 예외)
- [ ] 이벤트, 콜백, 넘기는 작업은 등록·발행하는 자리에서 무슨 일이 언제 도는지 보인다
- [ ] 이름으로 내용을 알 수 없는 실행 객체를 돌려줘 안을 뒤지게 하는 구조가 없다
- [ ] 응답 전에 끝나야 하는 일은 서비스가 명시적으로 부르고, 나중에라도 끝나야 하는 일은 그 책임이 업무 저장과 같은 트랜잭션에 남는다
- [ ] 이벤트를 쓴 자리는 리스너 실패가 요청 결과를 뒤집지 않게 실행 시점과 실패 처리(누가 기록·재시도·확인하나)가 정해져 있다
- [ ] 꼭 지켜야 할 순서를 리스너 `@Order` 에 숨기지 않고, 리스너가 반환값으로 다음 이벤트를 내지 않는다
- [ ] 리스너는 받는 기능의 `port/in` 에 넘기고(서비스 직접 호출은 ADR-017 생략 조건일 때만), out 어댑터를 직접 부르지 않는다
- [ ] 이벤트에 영속 엔티티, 요청 객체, 토큰이 없고, 실은 개인정보는 최소이며 저장 자리의 보관·접근·로그 노출이 통제되고, 받는 쪽이 권한과 범위를 다시 확인한다
- [ ] 동작을 바꾸는 advice 는 적용 자리에 뜻이 읽히는 표시가 있고, 표시 없는 패턴 advice 는 관측만 한다
- [ ] 필터·인터셉터, 자동 실행, 조건부 빈, 늦게 도는 일, 메시지 실패 경로가 한 자리에서 찾아진다

### 안티패턴

| 안티패턴 | 올바른 패턴 |
|---------|-----------|
| `stream(runs.report(key), response)`, `slot.claim()` | `reportJobService.startReportJobAndWriteResult(targetKey, resultLines)`, `runningFlag.markStartedOrReject()` |
| 람다를 든 실행 객체를 돌려주고 위로 돌아가 다른 자리에서 실행 | 그 단계에서 이름 있는 메서드를 부른다. 미뤄야 하면 이름 있는 작업(`sendReceiptTask`)이나 이벤트로 |
| `DataChanged` 이벤트와 `onEvent` 리스너 | `OrderPlacedEvent` 와 `sendReceiptOnOrderPlaced` |
| 층마다 `process()`, `handle()`, `execute()` | 층마다 하는 일(`validateTarget`, `startReportJob`, `writeResultLine`) |
| 같은 기능의 필수 단계(재고 차감)를 이벤트로 넘기고 리스너 `@Order(1)` 로 순서를 맞춤 | 서비스가 `inventory.reserve(...)` 를 명시적으로 부른다 |
| 리스너가 `mailClient.send(...)` 로 out 어댑터를 바로 부름 | 리스너는 `sendReceiptUseCase.sendFor(orderId)` 에 넘기고, 유스케이스가 out 포트를 부른다 |
| 리스너 예외를 `catch (Exception e) {}` 로 삼켜 요청을 살림 | 실행 시점(커밋 뒤, 정해진 실행기)과 실패 기록·재시도 책임을 정한다 |
| `execution(* ..service..*(..))` 로 권한 확인이나 값 바꾸기를 검 | 메서드에 `@PreAuthorize` 처럼 뜻이 읽히는 표시를 단다. 패턴 advice 는 관측만 |

## 다른 언어에서

- 원칙은 같다. Kotlin 은 스코프 함수(`let`, `also`, `run`)를 겹쳐 흐름을 가리지 않고, TypeScript 는 미들웨어·데코레이터·이벤트 이름이, Python 은 데코레이터·콜백·`create_task` 에 넘기는 코루틴 이름이 맡은 일을 말하게 한다. 표준 라이브러리 함수 이름은 위 금지와 상관없다.

## Consequences

### 긍정적
- 코드의 주인이 입력부터 흐름을 따라가고, 그 흐름으로 업무를 이해한다.
- AI 가 짠 코드도 사람이 확인할 수 있고, 그래야 나머지 ADR 도 확인된다.

### 부정적
- 이름이 길어지고 짓는 데 시간이 든다. 좋은 이름이 안 나오면 구조가 이상하다는 신호다.
- 판정이 주인의 판단에 기댄다. 읽히는지 자체는 리뷰로 판단하고, 일부 선언·배치 관례(리스너·입구의 자리, 애스펙트 허용 목록)만 `checks/` 가 기계로 본다. 기계 검사를 통과했다고 흐름이 보장되지는 않는다.
- 이벤트와 AOP 를 좁혀, 같은 기능 안에서 이벤트로 느슨하게 풀던 자리가 명시적 호출로 돌아와 서비스 코드가 길어질 수 있다.

## 다시 볼 때

처음 적용하는 프로젝트에서 주인이 따라가지 못한 자리를 모아, 이 ADR 의 기준과 예시를 고친다.
