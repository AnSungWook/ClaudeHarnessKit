# ADR-002: 값은 정적 팩토리로 만들고, 판단은 그 클래스가 다 가진다

## Status

Accepted

## Date

2026-10-30

## Intent

"이 값이 어디서 어떻게 정해지나" 를 한 클래스만 보면 알 수 있게 한다. 서비스는 흐름만 읽히게 둔다.

## Context

- 기존 상태: 서비스가 응답·결과 객체를 직접 `new` 로 조립하고, 상태값·기본값·실패 문구 같은 판단을 생성 인자 안에서 삼항 연산자와 문자열 조립으로 정한다.
- 문제점: 같은 조립이 서비스 여러 곳에 풀려 있어 필드 하나를 빠뜨려도 컴파일이 못 잡고 화면에서야 드러난다. 판단을 바꾸려면 서비스 전체를 뒤져야 한다.
- 제약 조건: "바깥 `new` 전면 금지" 로 검사를 걸면, 검사를 맞추려고 판단 없는 껍데기 팩토리가 생긴다. 막을 것은 `new` 가 아니라 타입 밖의 판단이다.

## Decision

**판단이 드는 값은 그 타입의 정적 팩토리로 만들고, 값을 정하는 판단(상태, 부분 성공, 실패 사유, 재시도 여부, 기본값, 집계)은 그 타입 안에 둔다. 서비스는 읽기 쉬운 이름의 호출을 나열하는 흐름만 든다.**

- 팩토리 이름: 변환은 `of(원본)`(원본을 보고 갈림까지 타입 안에서 판단하는 변환도 `of(원본...)`), 호출하는 쪽이 갈림을 골라 부르는 생성은 `succeeded(...)`·`failed(...)` 처럼 갈림을 이름에, 필드 하나만 바꾼 사본은 `withXxx(...)`.
- 생성자 `new`: 판단 없는 값은 어느 층이든(층 정의는 ADR-005) 생성자로 만들어도 된다. 금지하는 것은 생성되는 타입 밖에서 하는 판단·계산(생성 인자 안의 조건, 문자열 조립, 계산)이다. 팩토리 안의 계산은 괜찮다.
- 생성되는 타입 밖(그 타입의 팩토리가 아닌 서비스, 어댑터 등)에서 생성 인자에 조건(`? :`)·문자열 조립(`+`)·계산을 넣으면 어느 층이든 위반이다. 판단이 바깥에 있다는 뜻이니 그 타입의 팩토리로 옮긴다. 그 타입 자신의 팩토리 안에서는 괜찮다.
- 이름뿐인 팩토리 금지: 본문이 `return new 자기타입(매개변수 그대로)` 뿐이면 생성자의 복사본이다. 판단이 없으면 생성자를 쓴다.
- 잘못된 값은 만들어질 수 없게 한다. 값 객체는 생성자(또는 팩토리)에서 불변 조건을 검사하고, 어기면 바로 예외를 낸다 - 반쯤 채운 객체가 돌아다니지 않게. 이 검사는 프로그래밍 오류를 막는 마지막 방어선이다.
  - 사용자 입력이 틀린 경우(요청 값 검증)는 경계(요청 검증, 서비스 입구)에서 먼저 걸러 업무 사유 예외로 낸다(ADR-006). 생성자의 범용 예외에 기대어 사용자에게 오류를 보이지 않는다.
- 같은 조립이 두 자리에 있으면 팩토리 하나로 모은다.
- 인자가 많을 때는 함께 다니는 인자 묶음이 업무 단위인지 본다. 같은 묶음이 여러 메서드를 같이 다니고 그 값으로 하는 판단·계산이 있으면 그 이름의 record 로 묶고 판단을 record 메서드로 옮긴다. 인자 수만 맞추려는 껍데기 묶음은 만들지 않는다.
- 원시 타입을 값 객체로 감싸는 것도 같다. 검증, 형식 바꾸기, 계산, 판단 같은 규칙이 있을 때만 감싼다. 칸만 담은 값 객체는 만들지 않는다. 다른 빈이 있어야 하는 판단(등록돼 있는지 등)은 값 객체가 아니라 서비스가 맡는다.
- **판단이 붙는 목록은 일급 컬렉션으로 둔다.** `List<X>` 를 그대로 돌리지 않고 그 목록을 든 record 에 합계, 거르기, 비었는지 같은 판단을 메서드로 둔다. 판단이 없는 목록은 `List` 그대로다 - 감싸기만 한 일급 컬렉션은 껍데기 값 객체와 같다.
  - 따로 읽어 온 두 목록(다른 기능의 값을 키 목록으로 받은 것, ADR-017)을 짝 지어 쓰면, 짝 맞추기와 짝이 없을 때의 처리, 그 짝으로 하는 판단을 그 묶음의 일급 컬렉션이 든다. 서비스는 읽고, 묶음을 만들고, 묶음의 메서드를 부른다.

```java
// 전: 짝 맞추기와 판단이 서비스에 풀려 있다
Map<Long, Category> categories = categoryUseCase.findByIds(categoryIdsOf(orders)).stream()
        .collect(toMap(Category::id, identity()));
List<Order> refundable = orders.stream()
        .filter(o -> categories.get(o.categoryId()) != null && categories.get(o.categoryId()).refundable())
        .toList();

// 후: 서비스는 흐름만, 짝과 판단은 일급 컬렉션 안
OrdersWithCategory orders = OrdersWithCategory.of(orderList, categoryUseCase.findByIds(categoryIdsOf(orderList)));
List<Order> refundable = orders.refundable();
```

```java
// 전: 서비스가 상태를 정하고 인자를 밀어 넣는다
return new OrderResult(order.id(), payment.approved() ? Status.PAID : Status.PENDING,
        payment.approved() ? null : "결제 대기: " + payment.reason(), clock.instant());

// 후: 서비스는 흐름만, 판단은 타입 안
return OrderResult.of(order, payment, clock);
```

### 체크리스트

- [ ] 생성자 `new` 는 판단 없는 값에 쓴다(어느 층이든 허용). 판단이 드는 값은 그 타입의 팩토리로 만든다
- [ ] 생성되는 타입 밖에서 생성 인자에 `? :`, 문자열 `+`, 계산이 없다(그 타입의 팩토리 안은 괜찮다)
- [ ] 본문이 `return new 자기타입(인자 그대로)` 뿐인 팩토리가 없다
- [ ] 상태·기본값·실패 문구 같은 판단이 서비스가 아니라 그 값의 타입 안에 있다
- [ ] 같은 조립이 두 자리 이상에 풀려 있지 않다
- [ ] 값 객체 생성자(또는 팩토리)가 불변 조건을 검사한다
- [ ] 사용자 입력 오류는 생성자 예외가 아니라 경계의 사유 예외로 나간다
- [ ] 값 객체와 일급 컬렉션에 규칙(검증, 계산, 판단)이 있다 - 칸만 감싼 것이 없다
- [ ] 따로 읽은 두 목록의 짝 맞추기와 판단이 서비스가 아니라 묶음 타입 안에 있다

### 안티패턴

| 안티패턴 | 올바른 패턴 |
|---------|-----------|
| 서비스가 `new Result(a, cond ? X : Y, "..." + b)` 로 조립 | `Result.of(원본...)` / `Result.succeeded(...)` 가 판단까지 든다 |
| 검사를 맞추려고 `static Result of(a, b) { return new Result(a, b); }` | 판단이 없으면 생성자를 그대로 쓴다 |
| 별도 Mapper 클래스·MapStruct 로 변환 | 만들어지는 타입이 원본을 아는 `of(원본)` |
| 빌더로 필수 필드를 채움 | 팩토리·생성자 인자로 필수 필드를 컴파일 때 강제 |
| 엔티티의 `toResponse()` | 응답 타입의 `of(entity)` - 엔티티가 화면을 모르게 |
| 인자 수만 줄이려는 값 없는 묶음 record | 판단·계산을 함께 가진 업무 단위 record |
| `record OrderId(long value) {}` 처럼 칸만 감싼 값 객체 | 규칙이 없으면 `long` 그대로, 규칙이 생기면 그때 감싼다 |
| 서비스마다 `Map` 을 만들어 `map.get(o.categoryId())` 로 짝 맞추고 null 검사 | 묶음 일급 컬렉션의 `of(...)` 와 판단 메서드 |

## 다른 언어에서

- Kotlin: `data class` + `companion object` 의 `of(...)`. 판단 없는 팩토리는 기본 생성자로 충분하다.
- TypeScript: 클래스의 `static of(source)` 또는 같은 모듈의 생성 함수(`createOrderResult(order, payment)`). 객체 리터럴을 서비스에서 직접 조립하지 않는다.
- Python: `@classmethod def of(cls, source)` 또는 `@dataclass(frozen=True)` + 생성 함수. 생성 검사는 `__post_init__`.

## Consequences

### 긍정적
- 값의 출처와 판단이 한 파일에 모여, 바꿀 때 한 곳만 고친다.
- 서비스가 짧아져 흐름이 그대로 읽힌다.
- 필수 필드 누락을 컴파일에서 잡는다.

### 부정적
- 타입마다 팩토리가 늘어 파일 수가 는다.
- 생성 인자 밖 판단 금지를 리뷰나 아키텍처 테스트(ArchUnit 등)로 따로 지켜야 한다.
