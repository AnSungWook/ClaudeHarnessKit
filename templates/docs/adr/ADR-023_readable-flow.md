# ADR-023: 입구에서 실제 일을 하는 클래스까지 몇 번만 열면 닿게 짠다

## Status

Accepted

## Date

2026-11-03

## Intent

처음 보는 사람이 입구(컨트롤러, 잡 실행, 메시지 수신)를 열고 그다음 열 클래스를 바로 알아, 몇 번 안에 실제 일을 하는 자리에 닿게 한다.
흔히 아는 프레임워크 모양(예: Controller → JobLauncher → JobConfig → Reader/Processor/Writer)이 코드에서 그대로 보이게 둔다.

## Context

- 기존 상태: 실행 하나에 겹침 막기, 대상 확인, 진행 상황 내보내기, 결과 판정 같은 부가 처리를 붙이면서, 그것마다 작은 클래스와 함수 묶음(람다를 들고 다니는 래퍼, 실행을 "잡아 둔" 객체, 줄 쓰기 전용 객체)을 하나씩 만든다.
  컨트롤러는 `stream(runs.inspection(key), response)` 한 줄이 되고, 그 안을 열면 `Slot`, `ClaimedRun`, `BatchRun`, `RunLines`, `ProgressRelay` 가 서로를 감싼다.
- 문제점: 각 클래스는 이유가 있고 작지만, 길을 따라가려면 대여섯 파일을 오가야 하고 어느 것이 핵심인지 안 보인다. 실제 Job 실행(`jobOperator.start`)은 세 겹 안쪽에 묻힌다.
  Spring Batch 를 아는 사람도 "JobConfig 하나에 Chunk 클래스 정도" 를 기대하고 열었다가 길을 잃는다.
- 제약 조건: 부가 처리(409 겹침 막기, 진행 줄, 종료 코드용 결과 줄)는 운영 요구라 걷을 수 없다. 줄이는 것은 기능이 아니라 겹이다.

## Decision

**핵심 흐름은 아는 모양 그대로 드러내고, 부가 처리는 한 자리에 모은다. 겹을 하나 더 만들 때는 그 겹이 없으면 무엇이 깨지는지 말할 수 있어야 한다.**

- 입구에서 실제 일을 하는 클래스까지 **세 번 안에** 닿게 한다. 배치라면 Controller → 실행 서비스 → JobConfig(그 안의 Step, Reader/Processor/Writer).
- 입구 메서드 본문을 읽으면 다음에 열 클래스와 메서드 이름이 바로 보여야 한다. 람다나 함수 객체를 만들어 넘기고 나중에 다른 자리에서 실행하는 식으로 흐름을 숨기지 않는다.
- 부가 처리(겹침 막기, 진행 상황, 결과 판정)는 기능 하나에 클래스 하나로 모은다. 한 가지 부가 처리를 위해 래퍼·홀더·릴레이를 여러 개로 쪼개지 않는다.
- 실행 결과를 "잡아 둔 실행" 같은 중간 객체로 들고 다니지 않는다. 시작 전 검사 → 실행 → 결과 정리를 한 메서드 안에 순서대로 적는다(`try/finally` 로 정리).
- 프레임워크가 이미 주는 것(JobLauncher, JobExecution 상태, Step 리스너)을 먼저 쓴다. 같은 일을 하는 우리 타입을 따로 만들지 않는다.
- 이 ADR 은 ADR-001 과 같은 쪽이다 - "서비스는 흐름만" 은 흐름이 한눈에 보인다는 뜻이고, 흐름을 여러 객체로 흩는 것은 그 반대다.

### 체크리스트

- [ ] 입구 클래스에서 실제 일을 하는 클래스(배치면 JobConfig)까지 세 번 안에 닿는다
- [ ] 입구 메서드 본문에 다음에 열 클래스·메서드가 이름으로 보인다
- [ ] 람다·함수 객체를 들고 다니다 다른 자리에서 실행하는 래퍼(`XxxRun`, `ClaimedXxx`, `XxxHolder`)가 없다
- [ ] 부가 처리 하나에 클래스가 하나다(진행 줄을 위한 클래스가 여럿이 아니다)
- [ ] 새 겹마다 "없으면 무엇이 깨지는지" 를 설명할 수 있다(PR 이나 주석 한 줄)

### 안티패턴

| 안티패턴 | 올바른 패턴 |
|---------|-----------|
| `stream(runs.inspection(key), response)` → `BatchRun.holding(release, lines -> ...)` → `ClaimedRun` → `Slot` | `jobRunner.run(INSPECTION, key, writer)` 한 메서드에서 잠금 → `jobLauncher.run(job, params)` → 결과 줄 → 잠금 해제 |
| 진행 줄을 위해 `RunLines`, `ResponseLines`, `ProgressRelay`, `RunProgress` 넷 | 진행 줄 쓰기 클래스 하나(`JobProgressWriter`)가 시작·진행·끝 줄을 다 쓴다 |
| `AtomicBoolean` 을 감싼 `Slot` 안에 Job 실행까지 넣기 | 잠금은 잠금만, Job 실행은 실행 서비스 본문에 그대로 |
| 프레임워크 실행 상태를 우리 결과 타입으로 다시 싸서 넘기기 | `JobExecution` 을 받아 결과 줄로 바로 바꾼다 |

## 다른 언어에서

- 원칙(아는 모양을 드러내기, 겹 줄이기, 흐름을 함수 객체로 숨기지 않기)은 같다.
- Kotlin: 확장 함수와 고차 함수로 흐름을 감싸는 것도 같은 기준 - 입구에서 다음 자리가 보여야 한다.
- TypeScript(Node): 미들웨어·데코레이터를 겹겹이 쌓아 실제 처리기가 안 보이게 하지 않는다. 라우터 → 서비스 → 작업 함수.
- Python: 데코레이터와 콜백 체인으로 흐름을 숨기지 않는다. 뷰 → 서비스 → 작업.

## Consequences

### 긍정적
- 처음 보는 사람도 프레임워크 지식만으로 흐름을 따라간다.
- 핵심 자리(실제 실행)가 묻히지 않아 장애 때 볼 곳이 바로 보인다.

### 부정적
- 한 메서드가 조금 길어진다(검사, 실행, 정리가 한자리에).
- 부가 처리를 다른 실행에서 다시 쓰려면 그때 가서 뽑아낸다 - 미리 쪼개지 않는다.
