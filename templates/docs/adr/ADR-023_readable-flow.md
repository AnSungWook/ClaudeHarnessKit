# ADR-023: 흐름은 입구에서 바로 따라갈 수 있게 짜고, 간접 층은 이유가 있을 때만 둔다

## Status

Accepted

## Date

2026-11-03

## Intent

코드를 처음 보는 사람이 입구(컨트롤러, 잡 실행, 메시지 수신)에서 실제 처리까지 몇 번 안 열고 닿게 한다.
프레임워크가 정한 표준 구조가 코드에서 그대로 보이게 둔다.

## Context

- 기존 상태: 실행 하나에 부가 관심사(동시 실행 막기, 대상 확인, 진행 보고, 결과 변환)를 붙일 때마다 래퍼, 홀더, 콜백을 든 객체를 하나씩 더한다. 입구 메서드는 객체를 조립해 넘기는 한 줄이 되고, 실제 처리는 그 객체들이 서로를 감싼 몇 겹 안쪽에서 나중에 실행된다.
- 문제점: 각 클래스는 작고 이유도 있지만, 흐름을 따라가려면 여러 파일을 오가야 하고 어느 것이 핵심인지 안 보인다. 프레임워크의 표준 구조(MVC 의 Controller·Service, 배치의 Job·Step·Reader/Processor/Writer, 메시지의 Listener)를 아는 사람도 그 구조를 코드에서 못 찾는다. 장애가 나면 볼 자리를 찾는 데 시간이 든다.
- 제약 조건: 부가 관심사 자체는 운영 요구라 걷을 수 없다. 줄이는 것은 기능이 아니라 겹이다. 층 나눔(ADR-004)과 판단의 소유(ADR-001)는 그대로 지킨다 - 층을 없애자는 것이 아니라 층 안에서 겹을 늘리지 말자는 것이다.

## Decision

**입구에서 실제 처리까지는 이름 있는 메서드를 직접 부르는 길 하나로 보이게 하고, 간접 층은 그것이 없으면 무엇이 깨지는지 말할 수 있을 때만 둔다.**

- 기본 경로는 입구 → 응용 서비스 → 실제 처리(도메인 또는 프레임워크 정의, 예: 배치의 Job 정의)다. 입구에서 실제 처리까지 **세 파일 안에** 닿는다.
- 프레임워크의 표준 구조를 그대로 드러낸다. 프레임워크가 이미 주는 것(실행기, 실행 상태, 리스너, 인터셉터)을 같은 일을 하는 자체 타입으로 다시 감싸지 않는다.
- 입구 메서드 본문에서 다음에 열 클래스와 메서드가 이름으로 보여야 한다. 람다나 함수 객체를 만들어 다른 객체에 맡기고 나중에 실행하는 지연 실행은 프레임워크가 그 모양을 요구할 때만 쓴다.
- 부가 관심사 하나는 클래스 하나가 든다. 한 관심사를 래퍼, 홀더, 릴레이로 나누지 않는다. 여러 실행이 같은 부가 관심사를 쓰면 공통 클래스 하나나 프레임워크 확장점(리스너, 인터셉터, AOP)에 둔다.
- 위임만 하는 클래스를 두지 않는다. 받은 것을 그대로 다음에 넘기기만 하면 그 클래스를 걷고 직접 부른다.
- 한 실행의 시작 전 검사 → 실행 → 정리는 한 메서드 안에 순서대로 적고, 정리는 `try/finally` 로 한다. 실행을 "잡아 둔" 중간 객체를 만들어 들고 다니지 않는다.
- 미리 쪼개지 않는다. 두 번째 쓰임이 실제로 생길 때 뽑는다.
- 겹을 더할 때는 그 이유(없으면 무엇이 깨지는지)를 PR 이나 주석 한 줄로 남긴다(ADR-009).

```java
// 전: 입구에서 무엇이 실행되는지 안 보인다. 실제 실행은 세 겹 안쪽 람다에 있다
@PostMapping("/jobs/report")
public void run(HttpServletResponse response) {
    stream(runs.report(), response);              // runs → Slot → ClaimedRun → BatchRun(lambda)
}

// 후: 다음에 열 자리가 이름으로 보이고, 검사 → 실행 → 정리가 한 메서드에 있다
@PostMapping("/jobs/report")
public void run(HttpServletResponse response) throws IOException {
    jobRunner.run(reportJob, ProgressWriter.of(response));
}

public void run(Job job, ProgressWriter progress) {
    if (!running.compareAndSet(false, true)) {
        throw new JobAlreadyRunningException(job.getName());
    }
    try {
        JobExecution execution = jobLauncher.run(job, parametersNow());
        progress.end(execution);
    } finally {
        running.set(false);
    }
}
```

### 체크리스트

- [ ] 입구에서 실제 처리(배치면 Job 정의)까지 세 파일 안에 닿는다
- [ ] 입구 메서드 본문에 다음에 열 클래스와 메서드가 이름으로 보인다
- [ ] 람다·함수 객체를 들고 다니다 다른 자리에서 실행하는 래퍼(`XxxRun`, `ClaimedXxx`, `XxxHolder`)가 없다. 프레임워크가 요구한 자리는 예외
- [ ] 위임만 하는 클래스가 없다
- [ ] 부가 관심사 하나에 클래스 하나다
- [ ] 프레임워크가 주는 실행 상태·리스너를 같은 일의 자체 타입으로 다시 감싸지 않았다
- [ ] 새로 더한 겹마다 이유 한 줄이 있다

### 안티패턴

| 안티패턴 | 올바른 패턴 |
|---------|-----------|
| 입구가 `handle(prepare(request))` 처럼 객체를 조립해 넘기기만 한다 | `orderService.place(command)` 처럼 다음 자리를 이름으로 부른다 |
| `Runnable`·`Function` 을 든 홀더를 만들어 넘기고 다른 객체가 나중에 실행 | 그 자리에서 메서드를 직접 부른다 |
| 진행 보고 하나에 `Lines`, `Writer`, `Relay`, `Progress` 여러 클래스 | 진행 보고 클래스 하나(`ProgressWriter`)가 시작·진행·끝을 다 쓴다 |
| 잠금 객체 안에 실행 로직까지 넣기 | 잠금은 잠금만, 실행은 서비스 본문에 |
| 프레임워크 실행 결과(`JobExecution`)를 자체 결과 타입으로 다시 감싸 여러 겹 넘기기 | 받은 그대로 쓰고, 필요한 자리에서 한 번 바꾼다 |
| 받은 인자를 그대로 다음에 넘기기만 하는 클래스 | 걷고 직접 부른다 |
| 쓰임이 하나인데 "나중을 위해" 인터페이스와 구현을 나눔 | 쓰임이 둘이 될 때 나눈다(포트가 필요한 경계는 ADR-004 대로) |

## 다른 언어에서

- 원칙(표준 구조를 드러내기, 직접 호출, 관심사 하나에 하나, 위임만 하는 층 금지)은 같다.
- Kotlin: 확장 함수, 고차 함수, 스코프 함수로 흐름을 감싸 실제 처리가 안 보이게 하지 않는다.
- TypeScript(Node): 미들웨어와 데코레이터를 겹겹이 쌓아 처리기가 안 보이게 하지 않는다. 라우터 → 서비스 → 작업 함수.
- Python: 데코레이터와 콜백 체인으로 흐름을 숨기지 않는다. 뷰(또는 핸들러) → 서비스 → 작업.

## Consequences

### 긍정적
- 처음 보는 사람이 프레임워크 지식만으로 흐름을 따라간다.
- 실제 처리 자리가 묻히지 않아 장애 때 볼 곳이 바로 보인다.
- 클래스 수가 줄어 바꿀 때 건드릴 자리가 적다.

### 부정적
- 한 메서드가 조금 길어진다(검사, 실행, 정리가 한자리에).
- 부가 관심사를 다른 실행에서 다시 쓰려면 그때 뽑아내야 한다.
