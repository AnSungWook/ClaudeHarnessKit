# ADR-023: 입력을 받은 자리부터 사람이 따라 읽을 수 있을 만큼 복잡도를 낮춘다

## Status

Accepted

## Date

2026-11-03

## Intent

요청이나 실행 명령을 받은 자리에서 읽기 시작한 사람이 그 입력이 어디로 가서 무엇이 되는지를 따라갈 수 있게 한다.
기능은 그대로 두고, 따라 읽기를 막는 복잡도만 줄인다.

## Context

- 기존 상태: 기능을 붙일 때마다 작은 클래스, 래퍼, 콜백이 하나씩 늘어난다. 하나하나는 이유가 있지만 모이면 입력이 어디로 흘러가는지 안 보인다.
- 문제점: 입구를 열어도 다음에 무엇을 열어야 할지 모른다. 실제 처리가 여러 겹 안쪽에 묻혀, 프레임워크를 아는 사람도 익숙한 구조를 코드에서 못 찾는다. 고치거나 장애를 볼 때 길을 찾는 데 시간이 든다.
- 제약 조건: 필요한 기능(겹침 막기, 진행 보고, 결과 정리 등)은 걷지 않는다. 층 나눔(ADR-004)과 판단의 소유(ADR-001)도 그대로 지킨다. 줄이는 것은 따라 읽기를 막는 겹이다.

## Decision

**입력을 받은 자리에서 시작해 읽어 내려갈 때 다음에 볼 곳이 바로 보이도록 짠다. 그렇게 안 읽히면 기능이 아니라 구조를 줄인다.**

- 판단 기준은 "처음 보는 사람이 입력부터 따라갈 수 있는가" 다. 파일 수나 깊이 같은 숫자로 정하지 않는다.
- 프레임워크의 익숙한 구조(Controller → Service, Job → Step, Listener → Handler)가 코드에서 그대로 보이게 둔다. 프레임워크가 이미 주는 것을 같은 일을 하는 자체 타입으로 다시 감싸지 않는다.
- 흐름은 이름 있는 메서드 호출로 이어지게 한다. 콜백이나 함수 객체에 실행을 맡겨 다른 자리에서 돌게 하는 모양은 프레임워크가 요구할 때만 쓴다.
- 한 가지 일을 위해 클래스를 여러 개로 잘게 나누지 않는다. 위임만 하는 클래스는 걷는다.
- 미리 나누지 않는다. 다시 쓸 자리가 실제로 생기면 그때 뽑는다.
- 구조를 더할 때는 그것이 왜 필요한지 한 줄로 설명할 수 있어야 한다(PR 이나 주석, ADR-009).

### 체크리스트

- [ ] 입력을 받는 자리부터 읽어 내려가면 다음에 볼 곳이 바로 보인다
- [ ] 프레임워크의 익숙한 구조가 코드에서 그대로 보인다
- [ ] 콜백이나 함수 객체로 실행을 넘겨 흐름이 숨겨진 자리가 없다(프레임워크가 요구한 자리는 예외)
- [ ] 한 가지 일이 여러 클래스로 잘게 나뉘어 있지 않고, 위임만 하는 클래스가 없다
- [ ] 새로 더한 구조마다 왜 필요한지 설명이 있다

### 안티패턴

| 안티패턴 | 올바른 패턴 |
|---------|-----------|
| 입구가 객체를 조립해 넘기기만 해서 무엇이 실행되는지 안 보인다 | 다음에 부르는 서비스와 메서드가 이름으로 보인다 |
| 실행을 람다로 싸서 다른 객체가 나중에 돌린다 | 그 자리에서 메서드를 직접 부른다 |
| 진행 보고 같은 한 가지 일이 여러 클래스로 나뉘어 서로를 감싼다 | 그 일은 클래스 하나가 든다 |
| 받은 것을 그대로 다음에 넘기기만 하는 클래스 | 걷고 직접 부른다 |
| 쓰임이 하나인데 "나중을 위해" 나눠 둔 구조 | 쓰임이 생길 때 나눈다 |

## 다른 언어에서

- 원칙(입력부터 따라 읽을 수 있게, 익숙한 구조를 드러내기, 흐름을 숨기지 않기)은 같다.
- Kotlin: 고차 함수와 스코프 함수를 겹쳐 흐름을 가리지 않는다.
- TypeScript(Node): 미들웨어와 데코레이터를 겹겹이 쌓아 처리기를 가리지 않는다.
- Python: 데코레이터와 콜백 체인으로 흐름을 가리지 않는다.

## Consequences

### 긍정적
- 처음 보는 사람도 입력부터 흐름을 따라간다.
- 고치거나 장애를 볼 때 볼 곳을 빨리 찾는다.

### 부정적
- 메서드 하나가 조금 길어질 수 있다.
- 다시 쓸 일이 생기면 그때 뽑아내는 수고가 든다.
